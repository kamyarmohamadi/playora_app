# بررسی امنیتی RPCهای ارتباطات اجتماعی — Playora

تاریخ بررسی: 2026-10-23  
مخزن: `kamyarmohamadi/playora_app`  
شاخه: `feature/playora-platform-game-plugin-architecture-2026-10-22`  
محیط بررسی زنده: پروژه توسعه Supabase با شناسه `nnowvfewtrfurnluhflt`

## خلاصه

Supabase Security Advisor سه هشدار برای اجرای توابع `SECURITY DEFINER` در schema عمومی گزارش می‌کند:

- `public.list_social_relationships()`
- `public.send_friend_request(text)`
- `public.respond_friend_request(uuid, text)`

بررسی فقط‌خواندنیِ تعریف‌های زنده نشان داد که هر سه تابع:
- از `SECURITY DEFINER` استفاده می‌کنند و `search_path` را خالی می‌کنند.
- هویت را از `auth.uid()` می‌گیرند و در بدنه تابع پیش از کار اصلی بررسی مجوز انجام می‌دهند.
- از طریق ACL زنده برای `authenticated` قابل اجرا هستند؛ اجرای `PUBLIC` و `anon` در ACL مشاهده‌شده اعطا نشده است.
- با این وجود، هشدار Advisor همچنان معتبر است: این‌ها نقاط ورودی عمومی API هستند که با امتیاز مالک تابع اجرا می‌شوند؛ بررسی کد فعلی جای تست مستقل امنیتی را نمی‌گیرد.

## جزئیات مشاهده‌شده

### `list_social_relationships()`
- تنها ردیف‌های رابطه‌ای را که فرستنده یا گیرندهٔ آن کاربر جاری است انتخاب می‌کند.
- برای رابطهٔ مسدودشده، فقط وضعیت مرتبط با گیرنده را نمایش می‌دهد.
- ریسک باقی‌مانده: چون تابع با امتیاز بالاتر اجرا می‌شود، هر تغییر آینده در query یا شرط‌های مالکیت می‌تواند به نشت داده تبدیل شود؛ آزمون منفی با دو هویت واقعی ضروری است.

### `send_friend_request(text)`
- نام کاربری را اعتبارسنجی می‌کند، هدف را از پروفایل‌ها پیدا می‌کند، برای جلوگیری از درخواست تکراری قفل تراکنشی می‌گیرد و محدودیت تعداد درخواست دارد.
- پیام خطا برای نام کاربری ناموجود را عمومی/یکسان نگه می‌دارد.
- ریسک باقی‌مانده: مسیرهای هم‌زمان، محدودیت نرخ و تلاش برای هدف‌گیری کاربران دیگر باید با دو JWT مستقل و تست‌های رقابتی بررسی شوند.

### `respond_friend_request(uuid, text)`
- اقدام را به `accepted`، `declined` یا `blocked` محدود می‌کند.
- به‌روزرسانی را فقط وقتی انجام می‌دهد که درخواست در حالت `pending` و گیرنده برابر کاربر جاری باشد.
- ریسک باقی‌مانده: تست‌های منفی باید اثبات کنند فرستنده یا شخص ثالث نمی‌تواند درخواست متعلق به دیگری را پاسخ دهد.

## نکتهٔ سازگاری

هر سه تابع در بدنه از `auth.role()` استفاده می‌کنند. مستندات جاری Supabase این روش را deprecated می‌دانند و استفاده از role target/policy مناسب را توصیه می‌کنند. چون این توابع `SECURITY DEFINER` هستند، تبدیل مستقیم به `SECURITY INVOKER` یا حذف شرط نقش بدون تحلیل مجوزهای جدول ممکن است رفتار محصول را خراب کند یا دسترسی ناخواسته بدهد؛ هیچ‌کدام نباید بدون تست و بازبینی انجام شود.

## مسیر اصلاح امن

1. حفظ وضعیت فعلی در محیط زنده؛ این بررسی هیچ DDL یا تنظیمی را تغییر نداده است.
2. ایجاد migration اصلاحی فقط پس از تهیهٔ تست‌های رگرسیون برای مالکیت، عدم افشای رابطه‌ها، محدودیت نرخ، پاسخ‌گویی به درخواست و رقابت تراکنشی.
3. بررسی اینکه آیا می‌توان توابع را به schema غیرقابل‌دسترسی مستقیم از Data API منتقل کرد و فقط از یک لایهٔ کنترل‌شده فراخوانی نمود؛ این تغییر نیازمند هماهنگ‌سازی فراخوانی‌های frontend/RPC است.
4. اگر توابع در `public` باقی بمانند، نگه‌داشتن `search_path` امن، حداقل‌سازی ACL، استفاده از نام‌گذاری schema-qualified، و افزودن تست‌های ACL به CI.
5. اجرای تست‌های دو کاربر با JWT واقعی در staging، اجرای Security Advisor دوباره، و بررسی مستقل پیش از تولید.
6. تا تکمیل این موارد، این هشدارها را مانع انتشار تولید نگه دارید.

## شواهد و محدودیت‌ها

- Security Advisor در 2026-10-23 همین سه هشدار را برگرداند.
- تعریف‌های زنده و ACL از `pg_proc` و `pg_get_functiondef` با query فقط‌خواندنی خوانده شدند.
- تست زندهٔ مرورگر با دو حساب واقعی در این مرحله انجام نشده است.
- هیچ migration زنده اجرا نشد و هیچ بازی، پرداخت، واریز یا برداشت فعال نشد.
