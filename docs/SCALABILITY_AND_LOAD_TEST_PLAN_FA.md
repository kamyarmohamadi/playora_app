# Playora — برنامه ظرفیت‌پذیری و آزمون بار

آخرین بازبینی: 2026-10-23  
شاخه کاری: `feature/playora-platform-game-plugin-architecture-2026-10-22`

## الزام محصول

Playora باید برای رشد تا ۱۰۰٬۰۰۰ عضو و سناریوی سخت‌ترِ حضور هم‌زمان تعداد زیادی کاربر آماده طراحی شود؛ از جمله ورود هم‌زمان کاربران، کلیک روی یک قابلیت محبوب، جست‌وجو/بارگیری فهرست بازی‌ها، ایجاد یا پیوستن به اتاق، و بازی آنلاین. «۱۰۰ هزار عضو ثبت‌شده»، «۱۰۰ هزار نشست هم‌زمان» و «۱۰۰ هزار کاربر فعال در هر ثانیه» سه بار متفاوت‌اند و باید جداگانه سنجیده شوند.

این سند هدف طراحی و معیار پذیرش است، نه ادعای ظرفیت فعلی. هیچ عدد ظرفیتی تا زمان اجرای آزمون روی محیطی مشابه staging/production و ثبت نتایج، تأییدشده محسوب نمی‌شود.

## اصول معماری الزامی

- **بدون گلوگاه تک‌نقطه‌ای:** مسیرهای پرترافیک نباید به یک نمونه برنامه، یک پردازش محلی یا یک قفل سراسری وابسته باشند.
- **API بی‌حالت تا حد امکان:** نشست و وضعیت پایدار در سرویس مناسب نگهداری شود تا نمونه‌های API قابل افزایش/کاهش باشند.
- **دیتابیس محافظت‌شده:** connection pooling، محدودیت هم‌زمانی، query timeout، تراکنش‌های کوتاه، index بر اساس query واقعی، و بررسی `EXPLAIN ANALYZE`؛ از اتصال مستقیم و نامحدود هر کاربر به PostgreSQL جلوگیری شود.
- **درخواست تکراری امن:** برای ایجاد اتاق، حرکت بازی، جایزه و هر عملیات مالی، شناسه idempotency و قید یکتای سمت سرور متناسب با عملیات طراحی شود.
- **کنترل هجوم درخواست:** rate limit چندلایه بر اساس IP، کاربر، نشست، endpoint و منبع مشترک؛ صف/محدودیت هم‌زمانی برای کارهای سنگین؛ backpressure به‌جای پرکردن حافظه و connection pool.
- **کش با مرز درست:** کاتالوگ عمومی و محتوای کم‌تغییر قابل cache باشد؛ اطلاعات خصوصی، موجودی، مجوزها و وضعیت authoritative بازی از کش عمومی یا داده stale تصمیم‌گیری نشوند.
- **Realtime مقیاس‌پذیر:** اندازه و تعداد کانال‌ها، مجوز عضویت، fan-out پیام، heartbeat، reconnect با backoff و سقف reconnect آزمایش شوند. هر حرکت بازی باید سمت سرور اعتبارسنجی و ترتیب‌دهی شود.
- **کارهای ناهم‌زمان:** ایمیل، اعلان، گزارش‌گیری و پردازش‌های قابل‌تعویق از درخواست کاربر جدا شوند؛ صف‌ها دارای سقف، retry محدود، dead-letter و idempotency باشند.
- **شکست کنترل‌شده:** timeout، circuit breaker در محل مناسب، retry فقط برای عملیات امن، محدودیت اندازه payload، و پیام خطای قابل‌بازیابی.
- **امنیت در مقیاس:** rate limit جایگزین احراز هویت و RLS نیست. در بار بالا هم جداسازی کاربران، مجوز کانال و عدم نشت داده باید حفظ شود.
- **قابلیت مشاهده:** latencyهای p50/p95/p99، نرخ خطا، نرخ درخواست، اشغال pool، queryهای کند، صف‌ها، اتصال realtime، reconnect، مصرف CPU/RAM و هزینه سرویس ثبت شوند؛ لاگ‌ها نباید token یا داده حساس داشته باشند.

## سناریوهای آزمون اجباری

1. **بار پایه:** ورود، بازیابی نشست، بارگیری Home و Games، پروفایل و درخواست‌های معمول.
2. **هجوم به یک بخش:** تعداد زیادی کاربر در بازه کوتاه روی یک endpoint یا یک کارت/قابلیت کلیک کنند؛ بررسی صف، rate limit، پاسخ خطا و بازیابی.
3. **ترافیک اوج:** افزایش مرحله‌ای بار تا ۱۰۰٬۰۰۰ نشست هم‌زمان آزمایشی، مشروط به فراهم‌بودن زیرساخت و داده‌های آزمایش؛ نرخ عملیات واقعی جداگانه تعریف شود.
4. **بازی آنلاین:** تعداد زیادی اتاق و اتصال realtime، حرکت‌های معتبر/نامعتبر، پیام‌های چت، قطع و اتصال مجدد؛ تعداد بازیکنان، اتاق‌ها و پیام‌ها جداگانه گزارش شوند.
5. **Soak test:** بار پایدار طولانی برای یافتن memory leak، نشت connection، رشد صف و افت تدریجی عملکرد.
6. **Spike test:** جهش ناگهانی بار و اندازه‌گیری زمان بازگشت به وضعیت عادی.
7. **تست وابستگی:** کندی/قطع دیتابیس، realtime، صف یا سرویس خارجی؛ سیستم نباید با retry نامحدود یا مصرف نامحدود منابع فروبپاشد.
8. **تست صحت زیر بار:** کلیک/ارسال تکراری، رقابت هم‌زمان روی یک اتاق، حرکت هم‌زمان، موجودی و عملیات اتمی؛ بدون حرکت تکراری، داده گم‌شده، خرج دوباره یا دسترسی بین کاربران.
9. **تست امنیت زیر بار:** حمله پیام/درخواست پرتعداد، دورزدن محدودیت، دسترسی به منابع کاربر دیگر و سوءاستفاده از کانال realtime.
10. **تست هزینه و بازیابی:** برآورد هزینه در اوج، سقف autoscaling، هشدار هزینه، و تمرین backup/restore و rollback.

## معیارهای اولیه پذیرش

این مقادیر **هدف اولیه برای اندازه‌گیری و کالیبراسیون** هستند، نه تضمین فعلی؛ باید بر اساس نوع endpoint، منطقه جغرافیایی و هزینه زیرساخت نهایی شوند.

- APIهای معمول در محیط آزمون: هدف p95 کمتر از ۳۰۰ میلی‌ثانیه برای عملیات خواندن ساده و کمتر از ۵۰۰ میلی‌ثانیه برای تغییرات معمول، بدون احتساب تأخیر شبکه کلاینت.
- نرخ خطای غیرمنتظره زیر بار توافق‌شده: هدف کمتر از ۰٫۱٪؛ خطاهای کنترل‌شده rate limit جداگانه گزارش شوند.
- هیچ نقض RLS/مجوز، دوباره‌خرج‌کردن، نتیجه بازی ناسازگار یا از دست‌رفتن تراکنش پذیرفته نیست.
- صف‌ها، connection pool و حافظه باید محدود و قابل مشاهده باشند؛ بار بیش از ظرفیت باید با پاسخ کنترل‌شده مدیریت شود.
- آزمون ۱۰۰ هزار نشست هم‌زمان فقط زمانی پاس است که گزارش شامل مشخصات محیط، توزیع عملیات، نرخ درخواست، مدت آزمون، نتایج p50/p95/p99، نرخ خطا، منابع و محدودیت‌های مشاهده‌شده باشد.
- پس از هر تغییر عمده در API، schema، realtime یا زیرساخت، آزمون رگرسیون ظرفیت مرتبط تکرار شود.

## مسیر پیاده‌سازی

1. اندازه‌گیری baseline فعلی و شناسایی endpointها/queryهای پرترافیک.
2. تعریف workload واقعی: نسبت خواندن/نوشتن، تعداد بازی‌ها/اتاق‌ها، پیام realtime و نرخ کلیک.
3. بهینه‌سازی query و index با داده آزمون؛ pagination و محدودیت پاسخ در API.
4. پیاده‌سازی idempotency، محدودیت هم‌زمانی، rate limit و backpressure.
5. آزمون جداگانه Supabase Auth/Postgres/Realtime و تعیین سقف‌های واقعی سرویس/طرح میزبانی.
6. افزایش تدریجی ظرفیت API و کارهای async بر اساس اندازه‌گیری، نه حدس.
7. اجرای بار، spike و soak در staging؛ رفع گلوگاه‌ها و تکرار تا پاس‌شدن معیارها.
8. ثبت نتایج در checkpoint و چک‌لیست انتشار. هیچ موردی صرفاً به‌خاطر اضافه‌شدن کد تیک نمی‌خورد.
