## 1) تصمیم‌های تثبیت‌شده محصول

- نام محصول: **Playora**.
- زبان‌های نسخه اول: انگلیسی و فارسی؛ طراحی باید افزودن زبان‌های بعدی و RTL/LTR را بدون بازنویسی آماده کند.
- ورود: Google/Gmail OAuth با نشست امن، خروج، تمدید نشست و بازیابی خطا.
- شروع با سرویس‌های رایگان یا free tier؛ «رایگان» به معنای نامحدود یا تضمین دسترس‌پذیری نیست. سهمیه، محدودیت خواب/غیرفعالی، نگهداری داده و آستانه ارتقا باید پیش از انتشار بررسی شوند.
- هدف مرحله اول: پایلوت کوچک با چند صد حساب ثبت‌شده. این هدف، تضمین تعداد کاربران هم‌زمان نیست؛ ظرفیت فقط با آزمون مستند قابل ادعاست.
- معماری باید امکان رشد تدریجی را بدهد: stateless API تا حد امکان، دیتابیس مدیریت‌شده با connection pooling، migrationهای نسخه‌بندی‌شده، صف/Realtime قابل جایگزینی، تنظیمات محیطی و جداسازی ماژول بازی از هسته.
- بازی رایگان در اولویت است. ماژول بازی باید مستقل و قابل نصب/غیرفعال‌کردن باشد.
- کیف پول/سکه درون‌برنامه‌ای با ارز دیجیتال یکی نیست. نرخ محصول پیشنهادی مالک: 1 USD = 100 coins؛ این صرفاً قاعده محاسباتی پیشنهادی است و به‌خودی‌خود حق بازخرید یا ارزش پولی ایجاد نمی‌کند.
- کریپتو، برداشت واقعی، شرط‌بندی سکه‌های قابل‌خرید، جایزه پولی و دریافت کارمزد از بازی‌های پولی **تا بررسی حقوقی، انطباق، احراز هویت، ضدپول‌شویی، امنیت مالی و تأیید صریح مالک غیرفعال می‌مانند**.
- ارز/شبکه‌های آینده باید از تنظیمات کنترل‌شده و فهرست مجاز خوانده شوند؛ آدرس کیف پول ثابت فعلاً وارد کد یا UI عملیاتی نشود.
- نرخ تبدیل کریپتو باید از منبع نرخ قابل‌اعتماد با زمان آخرین به‌روزرسانی بیاید، با برچسب «تقریبی» و هشدار تغییر نرخ تا زمان تأیید تراکنش. CoinGecko فقط نامزد بررسی است؛ هنوز provider یا کلید/پلن آن انتخاب یا متصل نشده است.
- هشدار آدرس/شبکه اشتباه لازم است، اما هشدار جایگزین کنترل فنی شبکه، حداقل واریز، تأییدیه‌ها و reconciliation نیست.
- هویت عمومی مالک در پروفایل‌ها/صفحات عمومی نمایش داده نمی‌شود. این تعهد به معنای ناشناس بودن در برابر میزبان، بانک/پرداخت‌یار، ارائه‌دهنده KYC یا مراجع قانونی نیست.
- سن اعلامی بالای 18 سال به‌تنهایی برای محصول شرط‌بندی/برداشت کافی نیست. باید محدودیت کشور، مجوز، KYC/AML، sanctions، مالیات، مسئولیت پرداخت و الزامات مصرف‌کننده بررسی شود. تا آن زمان قابلیت‌های پول واقعی خاموش‌اند.
- نرخ کارمزد احتمالی 2% یا 5% فقط تنظیمات پیشنهادی و قابل‌تغییر است؛ انتخاب نهایی بعد از بررسی حقوقی، هزینه شبکه، هزینه provider و مدل اقتصادی انجام می‌شود.
- تصویر مرجع نهایی رابط هنوز باید از مالک دریافت شود؛ تا دریافت آن، تغییرات بصری بزرگ را قطعی تلقی نکنید.

- [ ] اگر PWA/Android خواسته شد: manifest، icons، offline behavior و تست نصب؛ بسته Android فقط پس از انتخاب مسیر build و امضای امن.
- [ ] نسخه‌بندی release، changelog، SHA و روش rollback.
- [ ] سیاست پشتیبانی، گزارش باگ و پاسخ به رخداد.

### مرحله K — پنل مدیریت آینده

- [ ] RBAC سمت سرور با نقش‌های support/moderator/admin/owner و اصل least privilege.
- [ ] MFA برای مدیران و محدودیت session.
- [ ] مدیریت اعضا با کمترین دسترسی لازم؛ مشاهده داده حساس با audit.
- [ ] مدیریت کاتالوگ، وضعیت بازی‌ها، version، approved origin و permissions.
- [ ] مدیریت گزارش‌های پشتیبانی و moderation.
- [ ] تنظیمات قابل‌تغییر: locale، feature flags، حدود نرخ، کارمزد پیشنهادی و provider فعال.
- [ ] تنظیمات کیف پول/شبکه فقط در صورت مجازشدن محصول مالی؛ دسترسی محدود، تأیید دو نفره و audit.
- [ ] لاگ تمام تغییرات مدیریتی، قبل/بعد، actor، timestamp و دلیل.
- [ ] تست IDOR/privilege escalation و تأیید جداسازی API پنل.
- [ ] پنل مدیریت از APIهای مستند استفاده کند و به جداول با دسترسی عمومی وصل نشود.

## 4) معیار نهایی «آماده تحویل»

نسخه نهایی فقط زمانی آماده اعلام می‌شود که build نصب‌پذیر، CI سبز، تست‌های E2E، بررسی امنیت/RLS، پیکربندی استقرار، backup/rollback و مستندات تحویل همگی شواهد قابل‌ردیابی داشته باشند. «بدون هیچ باگ» را نمی‌توان تضمین کرد؛ هدف، ریسک کنترل‌شده و کشف/رفع باگ با آزمون‌های قابل‌تکرار است.

## 5) قاعده پیگیری

بعد از هر مرحله:
1. تغییر کد/مدرک در همین شاخه ذخیره شود.
2. آزمون مربوطه اجرا و نتیجه ثبت شود.
3. فقط آیتمی که شواهد کافی دارد به `[x]` تغییر کند.
4. blocker و commit SHA در checkpoint ثبت شود.
5. `main` دست‌نخورده بماند؛ deploy یا migration زنده بدون اجازه صریح انجام نشود.
